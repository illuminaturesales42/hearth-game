## Executive summary

**Hearth is far healthier than a typical "audit me" project.** It is a disciplined, well-tested MVP with a pure/deterministic core, a real versioned save-migration chain, a working cloud-sync seam, on-device retention analytics, and 72 orders of hand-written story across 6 chapters. The brief's framing ("find every major weakness, chart the path from rough build to release") is answered honestly below — but the leading finding is that **the architecture is production-grade and should be preserved, not rebuilt.** The gaps are at the edges: tooling (no linter), accessibility, UX polish (native `confirm()` dialogs, missing explicit loading/offline states), test breadth (one e2e smoke), late-game design flatlining, and the unbuilt native-wrap + monetization layers that the team already scopes in `docs/roadmap-to-market.md`.

This audit deliberately aligns its roadmap with that existing `roadmap-to-market.md` rather than inventing a competing plan.

## 1. Codebase & Architecture Audit

### 1.1 What's strong (confirmed)

- **Clean layering.** `src/core/` is pure, DOM-free, deterministic game logic; `src/ui/` is DOM-string rendering subscribing to typed `Game` events; `src/data/` is serializable content; `src/platform/` + `src/health/` are drop-in seams for the native build. This separation is real and consistently held — e.g. `core/game.ts` imports no DOM, `core/board.ts` is entirely pure functions returning new state.
- **Immutability throughout.** Every board/state mutation returns a new object (`board.ts:23-33`, `withItem`/`withEmpty`; `game.ts` spreads state on every change). Matches the team's own coding-style rule.
- **Event-driven orchestration.** `Game` (`core/game.ts`) owns `GameState`, emits a well-typed `GameEvent` union (`game.ts:35-67`), and persists on every emit (`game.ts:254`). UI, analytics, and sync all subscribe independently — good decoupling.
- **Save system is genuinely robust** (see §1.3).
- **Retention math is pure and testable** (`core/retention.ts`) — D1/D7/D30, streaks, FTUE funnel, all clock-injected.

### 1.3 Save system (critical path) — confirmed healthy

`core/save.ts` is a highlight. Versioned localStorage at **v13** with a complete migration chain (`MIGRATIONS[8..12]`, `save.ts:27-49`), a final null-guard validating every required key (`save.ts:66-67`), 3-slot hourly rotating backups (`save.ts:99-112`), export/import (`save.ts:115-132`), and legacy-key adoption + a historical stamp-bug heal (`save.ts:56-58`). Round-trip is regression-tested (`tests/save.test.ts`). **One risk:** the migration chain and the null-guard are two places that must both be updated on any schema change — the header documents this, but it's a manual invariant with no compile-time enforcement. *Recommendation (P2):* add a test that asserts `migrateState` of a minimal v8 fixture yields every key the guard checks, so an omission fails CI.

### 1.4 Security & privacy (confirmed)

- **Cloud API is careful:** `functions/v1/save.ts` uses parameterized D1 SQL (`save.ts:120-126`), validates the envelope + device-key regex (`save.ts:48,66-73`), caps payload at 300 KB, and stores only the player's own export JSON (no health data). Conflict policy is rev-gated and mirrors the client.
- **Gaps:** (P1) **no rate limiting** on the Pages Function — a device key can hammer PUT; (P2) the anonymous bearer key *is* the account, client-generated, so anyone who learns a key owns that save (acceptable for the test fleet, must harden for real accounts); (P2) **no security headers / CSP** shipped (no `_headers` file present — *inferred* from absence; verify). Add a `public/_headers` with CSP, `X-Content-Type-Options`, `Referrer-Policy`.
- **XSS surface is mostly handled:** `screens.ts` escapes user-authored gratitude text via `esc()` (`screens.ts:19-21,128`). Dev-authored order/villager strings are injected into `innerHTML` unescaped, which is low-risk (content is trusted) but becomes a risk if any of that content ever becomes user- or network-supplied. Keep `esc()` discipline as the rule.

### 1.5 Testing, CI, dependencies

- **216 tests / 27 files** covering board, save, economy pacing, retention, duel AI, health, sync, collections, workshop, town requests — genuinely broad **unit/integration** coverage (confirmed by run).
- **e2e is one smoke spec** (`tests/e2e/smoke.spec.ts`): launch→merge→deliver→reload-persists. That's the single most valuable journey, but it's the only one. (P1) add FTUE-completion and energy-earn journeys.
- **CI** (`ci.yml`) runs test + build + uploads dist, and a separate Playwright job — solid. Deploy is gated on a `CLOUDFLARE_ENABLED` var (`deploy.yml`). No lint step (see A1).
- **Dependencies are lean and current:** Vite 6, vitest 2, TypeScript 5.6, Capacitor 8, wrangler 4 — no bloat, no obvious stale/insecure packages (*inferred*; run `pnpm audit` to confirm).

## 2. Game Design Audit

### 2.1 The loop as implemented (confirmed)

Real-world action / passive regen → **Hearth Energy** → tap producer to spawn (`game.ts:291-314`, costs 1 energy) → drag-merge up a chain (`board.ts:65-83`) → **deliver** the required chain+level to the current story order (`game.ts:467-495`) → earn energy + coins + a story beat + a villager bond → every 3rd delivery advances a **restoration zone** and the town visibly rebuilds. Parallel sinks: **Workshop** side-economy (craft resources → Town Requests / sell), **Builder's Yard** (long chains → sellable buildings), **Market** (cosmetic skins/decor/upgrades — coins buy beauty, never power), **Bonfire Duel** (hot-seat, banks spoils to a Repository usable for story). This is a complete, coherent merge-story loop.

### 2.2 Wellness integration (confirmed — the differentiator)

Energy sources are numerous and thoughtfully capped: steps/stairs/sleep via a tiered, idempotent **health ledger** (`health/health-energy.ts` — 1 energy/500 steps cap 20, sleep tiers 7h/8h, delta-only grants so re-sync is safe), plus self-report actions, guided meditation, logged meditation, recovery (cold plunge/sauna), gratitude journal (streak-multiplied), stargaze (real moon-phase-bonused, night-gated via `core/sun.ts`), and kindness-to-a-stranger (+selfie bonus). Streaks are **positive-only, never punished** (`actions.ts:110` resets to 1 with no penalty screen) — this is the anti-compulsion pillar, and it's actually coded, plus a 90-minute wind-down nudge (`main.ts:52-57`). **The "energy is never sold" pillar is enforced in the type system and comments, not just aspiration.**

### 2.4 Retention & session design

Strong on paper and in code: daily quests, streak milestones, achievements/collections, villager bonds that "remember" deliveries (`core/relationships.ts`, `game.ts:508-521`), an auto-written **Chronicle** of prose memories, gratitude flashbacks that resurface old good days, moon-phase stargaze, weather-reactive sky. The **day-2 return loop** (the single most important retention lever per the roadmap's own D1 gate) rests on the sunrise "New Day" claim + streak — adequate, but the audit flags (P1) that **push notifications are not built** (Phase B), so pre-native there is no re-engagement hook beyond habit.

### 3.3 Recommended lightweight design system

The art direction (dark navy/gold storybook) is already cohesive and authoritative. What's missing is a **code-level** system. Recommend a small, framework-free kit:
- **Tokens** (CSS custom properties, already partly in `styles.css`): color roles (`--ink`, `--gold`, `--ember`, surface tiers), spacing scale (4/8/12/16/24), radius, type ramp.
- **Builders** (`src/ui/kit.ts`): `card()`, `btn(kind)`, `modal(opts)` (with focus trap + `role=dialog`), `badge()`, `pillButton()`, `barMeter()`. Migrate screens onto them opportunistically.
- **Interaction states**: standard hover/active/disabled/`:focus-visible` rings; one toast/live-region.

## 8. Final Project Assessment

- **Completion:** ~70% of a soft-launch-ready **web** MVP; ~40% of a **native store** release.
- **Technical health: 8.5/10** — clean pure core, 216 green tests, robust save/sync, honest seams. Docked for no linter, one e2e, no crash reporting.
- **Game-design health: 7.5/10** — complete wellness-merge loop with a genuinely differentiated, ethically-enforced energy model and 72 orders of story. Docked for late-game restoration flatline and unbuilt monetization/social.
- **UX/UI health: 6.5/10** — cohesive art landing, warm copy, good empty states; docked for thin accessibility, native dialogs, implicit loading/offline states, no code-level design system.
- **Production readiness: 5/10 (store) · 7.5/10 (F&F web test).**

**Main launch blockers:** (operational) the one-time `wrangler login` for a permanent URL; (product) none critical — the P1 list is polish, not repair.

**Main technical risks:** save migration/guard drift (mitigated by the proposed test); silent sync/network degradation with no crash visibility (A4); iOS 7-day storage eviction until cloud saves ship natively (already the team's stated Phase B priority).

**Main design risks:** day-2 return with no push pre-native; late-game reward flatline (G1); scope creep from the expansive design bibles (the team's own "MVP-lite / Hearth Test" rule is the mitigation).

**Strongest parts:** the pure/deterministic core + save system; the wellness-energy model as a defensible, coded moat; the volume and warmth of written content; the discipline (tests, migrations, seams) already in place.

**Weakest parts:** accessibility; test breadth beyond units; late-game design payoff; the tooling gap (no lint); un-productionised native + monetization layers (expected at this stage).

**Recommended MVP feature set (ship the web F&F test on):** current loop + Ch 1–2 + wellness earning + save/sync + retention metrics + FTUE — all shipped. Add only P1 #1–4, #6 before pointing strangers at it.

**Delay until after launch:** subscription/chapter pass, social backend, localisation, licensed audio, code-splitting.

### The single best next task to begin immediately

**Adopt ESLint + Prettier and add a `lint` gate to CI (P1 #1).** It's small, unblocks quality on every subsequent task, will surface latent issues (floating promises, unused code) across the ~10.7k-LOC surface at once, and is the correct foundation before touching accessibility, the conflict modal, or the analytics sink. *Runner-up, if a player-facing win is wanted first:* remove `user-scalable=no` (U1) — a one-line accessibility fix.
